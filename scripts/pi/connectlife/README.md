# ConnectLife oven telemetry

This directory contains the read-only ConnectLife oven telemetry integration used by the EMS Pi runtime.

## Scope

The integration observes the oven through ConnectLife and publishes a normalized JSON state for EMS observability. It does **not** send appliance commands and does not create a new actuator path.

Runtime output:

```text
/home/jeroen/ems/runtime/state/oven-state.json
```

Schema:

```text
EMS_OVEN_STATE_V0.1
```

## Runtime path

```text
ConnectLife cloud
      │
      ▼
ovens returned by ConnectLifeApi.get_appliances()
      │
      ▼
oven_poll.py
      │
      ▼
oven_state.build_state()
      │
      ▼
/home/jeroen/ems/runtime/state/oven-state.json
```

The poller authenticates once and, in `--watch` mode, reuses the same API instance/session for repeated polls. The production service polls every 60 seconds. After three consecutive poll failures the process exits so systemd can restart it after 30 seconds.

## Normalized state

`oven_state.py` exposes the following EMS fields:

- `schema`: `EMS_OVEN_STATE_V0.1`
- `generatedAt`: UTC observation timestamp generated by the EMS adapter
- `source`: `CONNECTLIFE`
- `device`: ConnectLife device feature code
- `deviceName`: ConnectLife nickname
- `online`: derived from `offlineState == 1`
- `active`: `Status == 2`
- `state`: `IDLE`, `PREHEATING`, or `RUNNING`
- `setpoint_C`: active preheat/program setpoint; deliberately `null` while idle
- `measured_C`: `Oven_measured_temperature`
- `currentStep`: `Current_baking_step`
- `elapsed_s`: `Total_passed_time_seconds`
- `readOnly`: always `true`

State classification is currently:

```text
Status != 2                        -> IDLE
Status == 2 and Step_pre_bake_status == 2 -> PREHEATING
Status == 2 otherwise              -> RUNNING
```

ConnectLife can retain the previous program temperature after the oven becomes idle. The adapter therefore intentionally publishes `setpoint_C: null` in `IDLE` rather than exposing a stale setpoint as current EMS state.

## Files

- `oven_poll.py` — ConnectLife login/session, oven discovery, polling, atomic output and failure handling.
- `oven_state.py` — vendor-state to EMS-state normalization.
- `ems-connectlife-oven.service` — production systemd service.
- `install_systemd.sh` — guarded installation of credentials and service.

## Credentials and security

Credentials are local runtime secrets and must never be committed to GitHub.

The installer writes:

```text
/etc/ems/connectlife.env
```

with mode `0600`, owned by root. The service reads this file through `EnvironmentFile=`. The service runs as user/group `jeroen`, has `NoNewPrivileges=true`, `ProtectSystem=strict`, `ProtectHome=read-only`, and may write only to `/home/jeroen/ems/runtime/state`.

The Python environment currently used by the service is:

```text
/home/jeroen/ems/tools/connectlife-probe/.venv/bin/python
```

## Installation

From the repository root on the Pi:

```bash
bash scripts/pi/connectlife/install_systemd.sh
```

The installer validates that the virtual environment and `connectlife` package exist, asks for credentials without storing them in the repository, installs the unit, enables the service, and prints the resulting normalized state when available.

## Operational checks

```bash
systemctl status ems-connectlife-oven.service --no-pager -l
journalctl -u ems-connectlife-oven.service --since "10 minutes ago" --no-pager
cat /home/jeroen/ems/runtime/state/oven-state.json
```

Consumers must use `generatedAt` to detect staleness. A failed poll deliberately leaves the last valid JSON file intact.

## Architecture boundary

ConnectLife is a vendor-specific **read-only adapter**. Higher EMS layers may consume the normalized JSON state but must not depend on raw ConnectLife field names. Any future oven control capability requires a separate architecture/safety decision and must not be inferred from this telemetry integration.
