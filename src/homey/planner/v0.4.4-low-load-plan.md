# Planner v0.4.4 LOW-LOAD preparation

Status: **PREPARED, NOT DEPLOYED**

Baseline: `EM v2 | 45 Planner | 24h Energy Plan v0.4.3 SHADOW`

This change is intentionally prepared in GitHub first. The Homey Planner runtime remains on the v0.4.3 baseline until the normal migration gate can be completed.

## Objective

Reduce Homey API pressure and event fan-out while preserving planner policy and SHADOW safety semantics.

The current v0.4.3 performs a broad `Homey.logic.getVariables()` read and then performs two separate Logic writes:

- `EM2_Energy_Plan_24h`
- `EM2_Energy_Planner_Status`

Those writes can create multiple downstream change events. In a Homey already close to its API/rate-limit budget, the planner run can therefore become the tipping point even though it performs no physical actuator writes.

## Resolved runtime bindings

The canonical Logic variables have now been provisioned and their stable IDs captured:

- `EM2_Planner_Input` -> `39c7c169-34d7-4e14-a27b-520aca255032`
- `EM2_Energy_Planner_Snapshot` -> `b9f1232c-ac01-45fa-9453-ef95d998b138`

`EM2_Planner_Input` is produced by Core v0.10.17 from the existing single-reader Logic collection; Planner must therefore use targeted `Homey.logic.getVariable({id})` access and must not perform `getVariables()`.

`EM2_Energy_Planner_Snapshot` was provisioned by one controlled one-shot Homey setup flow, which was disabled immediately afterwards as `TEMP | Planner v0.4.4 Logic Provisioning [DONE]`. The provisioning flow performed no physical device writes.

## v0.4.4 target design

### 1. Canonical planner input snapshot

Use the upstream-produced Logic value:

`EM2_Planner_Input`

Schema: `EM2_PLANNER_INPUT_V0.1`

It contains only the values required by the planner:

```json
{
  "schema": "EM2_PLANNER_INPUT_V0.1",
  "generatedAt": "ISO-8601",
  "state": {},
  "warmWater": {},
  "contractPriceContext": {},
  "dayHistory": {},
  "contractType": "DYNAMIC|FIXED|UNKNOWN",
  "priceBuffer": []
}
```

The planner must no longer discover its inputs by scanning the complete Homey Logic variable collection.

### 2. Single planner output snapshot

Replace the two independent planner writes with one canonical output:

`EM2_Energy_Planner_Snapshot`

Schema: `EM2_ENERGY_PLANNER_SNAPSHOT_V0.1`

```json
{
  "schema": "EM2_ENERGY_PLANNER_SNAPSHOT_V0.1",
  "generatedAt": "ISO-8601",
  "plan": {},
  "status": {}
}
```

`plan` is the existing v0.4.3 plan object. `status` is the existing `EM2_Energy_Planner_Status` payload. Policy semantics do not change.

### 3. Event fan-out rule

Only `EM2_Energy_Planner_Snapshot` is allowed to trigger the event-driven Planner Shadow publisher.

The publisher must publish at most once per new `generatedAt` (or equivalent planner revision) and must be idempotent for duplicate Homey change events.

Legacy variables `EM2_Energy_Plan_24h` and `EM2_Energy_Planner_Status` may temporarily be derived by the publisher/compatibility layer if needed, but they must not independently trigger further downstream work.

### 4. Physical safety remains unchanged

v0.4.4 remains SHADOW/read-only:

- no device writes
- no Easee writes
- no boiler writes
- no Victron writes
- no change to existing actuator ownership

The following fields remain mandatory in the plan:

```json
{
  "controlMode": "SHADOW",
  "readOnly": true,
  "physicalWritePerformed": false
}
```

### 5. No policy change in this patch

The LOW-LOAD revision must preserve all v0.4.3 planning behaviour:

- 15-minute, 96-slot horizon
- Open-Meteo Hauwert shortwave-radiation forecast
- traceable base-load forecast
- Tesla PV-surplus-first opportunity policy
- Tesla deadline price optimisation only after PV preference
- warm-water PV-coverage-first ranking
- theoretical-only battery economic pairs

This is an execution/load refactor, not a planner-policy change.

## Candidate implementation pattern

The v0.4.4 runtime code must use the resolved IDs directly:

```js
const INPUT_ID='39c7c169-34d7-4e14-a27b-520aca255032';
const SNAPSHOT_ID='b9f1232c-ac01-45fa-9453-ef95d998b138';

const inputVar=await Homey.logic.getVariable({id:INPUT_ID});
const input=parse(inputVar?.value);
if (!input || input.schema !== 'EM2_PLANNER_INPUT_V0.1') {
  throw new Error('PLANNER_INPUT_MISSING_OR_INVALID');
}

// Existing v0.4.3 planner algorithm, fed only from `input`.

const snapshot = {
  schema: 'EM2_ENERGY_PLANNER_SNAPSHOT_V0.1',
  generatedAt: plan.generatedAt,
  plan,
  status
};

await Homey.logic.updateVariable({id:SNAPSHOT_ID,variable:{value:JSON.stringify(snapshot)}});
return true;
```

This gives the Planner one targeted Logic read and one Logic write per run. It must not call `Homey.logic.getVariables()` and must not write the two legacy Planner output variables.

## Acceptance / smoke gate

Before v0.4.4 can replace v0.4.3:

1. Planner is enabled only for the controlled smoke.
2. One manual planner run is performed.
3. Exactly one fresh canonical planner snapshot is observed.
4. Planner Shadow publisher picks up that snapshot once.
5. Public planner publication advances to the same `generatedAt`/revision.
6. Downstream Power Intent/public state remains consistent.
7. No physical actuator is intentionally triggered.
8. No Homey rate-limit is observed during the controlled chain.
9. Explicit PASS is recorded.
10. Planner is returned to disabled after the test.

Until all ten checks pass, v0.4.4 is **candidate only** and the migration gate remains closed.
