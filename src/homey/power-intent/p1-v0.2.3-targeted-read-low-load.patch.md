# Power Intent P1 v0.2.3 TARGETED-READ LOW-LOAD candidate

Status: **PREPARED, NOT DEPLOYED**

Baseline: active Homey Advanced Flow `EM v2 | 20 Power Intent | P1 v0.2.2 (Public decoupled)` (`19d9d8a6-ec32-4639-be5e-71e9f034d31b`), inspected directly on 2026-08-29.

## Runtime finding

The active v0.2.2 flow is already stage-2 decoupled from `EM2_Public_State`.

- Trigger: `EM2_Control_WW` variable changed.
- `EM2_Public_State` is publication-only and not a control dependency.
- The script is fail-closed and PURE SHADOW.
- It performs `Homey.logic.getVariables()` on every trigger.
- It exits early before writing `EM2_Power_Intent` when the previous valid Power Intent already has the same `sourceRevision`.

This means a time-only `EM2_Control_WW` update does **not** fan out into EV Gate/Adapter/Actuator writes when `sourceRevision` is unchanged, but it still causes one broad Logic collection enumeration.

## Why `EM2_Decision` must NOT become the sole trigger

Core revision changes only when the quantized state signature changes. `EM2_Control_WW` also contains WW scheduling/time-accounting semantics (for example run lock, fallback progression, price horizon and WW action) that can change without requiring a new generic Core state revision.

Therefore replacing the current trigger with only `EM2_Decision changed` could miss a valid WW target transition. Keep `EM2_Control_WW` as the downstream synchronization trigger.

## v0.2.3 low-load change

Replace the broad collection scan:

```js
const vars = await Homey.logic.getVariables();
```

with targeted reads of only the four Logic variables required by Power Intent:

```js
const stateVar    = await Homey.logic.getVariable({id: IDS.EM2_State});
const decisionVar = await Homey.logic.getVariable({id: IDS.EM2_Decision});
const wwVar       = await Homey.logic.getVariable({id: IDS.EM2_Control_WW});
const prevVar     = await Homey.logic.getVariable({id: IDS.EM2_Power_Intent});
```

Use stable Homey Logic IDs captured through controlled card autocomplete/binding before deployment. Do not add a discovery `getVariables()` fallback in steady state; missing/invalid bindings must fail closed and report configuration error.

### Optional fast path

Because the trigger itself is `EM2_Control_WW changed`, if a reliable trigger token containing the new value is available in Advanced Flow/HomeyScript without additional reads, consume that trigger payload for `wwVar` and reduce the targeted reads to State, Decision and previous Power Intent. Do not assume this capability without a controlled runtime proof.

## Expected load effect

Current v0.2.2 on every `EM2_Control_WW` change:

- 1 full Logic collection enumeration;
- 0 output write when `sourceRevision` is unchanged and previous intent is already valid;
- downstream cascade only when `EM2_Power_Intent` actually changes.

v0.2.3 target:

- 0 full Logic collection enumerations;
- 3-4 targeted Logic variable reads per trigger;
- same early-return/idempotency contract;
- unchanged downstream behavior.

This removes another repeated broad Homey API collection read from the five-minute Core path without changing control semantics.

## Safety invariants

- Keep trigger `EM2_Control_WW changed`.
- Keep schema `EM2_POWER_INTENT_V0.2`.
- Keep policy revision semantics equivalent to `P1_V0.2.2_PUBLIC_DECOUPLED` except version label.
- Keep exact revision-alignment checks for State, Decision and WW Control.
- Keep fail-closed EV target 0 W on mismatch/invalid input.
- Keep `readOnly=true`, `controlMode='SHADOW'`, `deviceWrites=false`.
- No device reads, device writes, network calls or polling.
- Do not enable Watchdog or any disabled publisher/history flows for this deployment.

## Deployment gate

1. Bind the stable Logic IDs for `EM2_State`, `EM2_Decision`, `EM2_Control_WW`, and `EM2_Power_Intent`.
2. Update only the Power Intent flow to v0.2.3.
3. Run one targeted SHADOW smoke only after Homey is no longer rate-limited.
4. PASS requires: no broad `getVariables()` path, revision coherence preserved, same numerical EV/WW projection for identical inputs, no physical writes, and exactly one downstream change only when intent semantics/revision genuinely change.
5. On `Too many requests`, stop immediately and leave the flow in the last known-safe state.
